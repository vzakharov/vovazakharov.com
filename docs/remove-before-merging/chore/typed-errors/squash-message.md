```
chore: ban bare new Error in favour of named error classes (#234)
```

```
A bare `new Error(…)` tells a reader that something failed but not
what, and a catch site has nothing to tell one failure from another.
#231 introduced `errorClass(name)` and `fetchOk` for its own modules;
this makes them the only way to throw, repo-wide.

A `no-restricted-syntax` rule at `error` bans both `new Error(…)` and
`Error(…)`, everywhere, tests included, with no scoped exemption. Every
existing site now throws a module-local class named for what failed,
and hand-rolled `fetch` + `!response.ok` checks go through `fetchOk`.

`asError(unknown)` sits beside `errorClass` and replaces the
`instanceof Error ? … : new Error(String(…))` coercion that
`vova/no-uncaused-rethrow` had forced into six places.
`eslint/masd-graph.ts` imports `error-class.ts` relatively, since a
module with no imports of its own never reaches the `@/` alias that
jiti skips. The self-containment line in `.claude/rules/eslint.md`
now guards only modules that reach `@/` transitively.
```
