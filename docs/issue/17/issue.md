## Body

`scripts/type-overlap-check.ts` counts only a type's **own** members: the named
constituents of an intersection are treated as inherited, which is precisely
what makes `& Base` clear a finding. The blind spot is one level up — the same
*combination* of bases, repeated.

PR #11 shipped exactly that:

```ts
type ProjectCardProps = Titled & Described & { techStack?: string; … };
type ArticleCardProps = Titled & Described & { url: string };
```

Both types are clean by the current gate — neither declares an own member the
other does — yet `Titled & Described` is duplicated in the same sense a member
would be: two things to change, and the compiler catches neither the drift nor
the duplication. It was caught in review, by eye, and fixed by naming the
combination (`type Summarized = Titled & Described`). Nothing stops the next one
landing green.

## What to add

A second pairwise pass over **named constituent sets**, mirroring the existing
member pass: for every pair of type aliases, intersect the sets of type
references each lists in its intersection, and report the pair when the shared
set is large enough. The fix a finding asks for is the same shape as today's —
name the combination and intersect *that* — so the "How to fix" block and the
naming families in `scripts/type-overlap-check.README.md` carry over unchanged.

Open questions for whoever picks this up:

- **Threshold.** The member pass floors at 1; the constituent pass cannot — one
  shared base is reuse working as intended, and is the end state every member
  finding is fixed into. The natural floor is 2. Whether that is its own
  `TYPE_OVERLAP_BASES_MIN` or a fixed constant is a judgment call.
- **Transitivity.** `Summarized = Titled & Described` means a type spelling
  `Summarized` and one spelling `Titled & Described` share a combination without
  sharing a token. Resolving constituents through the alias graph catches that;
  a purely syntactic pass does not. Syntactic is consistent with the rest of the
  detector and is probably the right first cut.
- **Reporting.** Findings should group the way member findings do (one group per
  identical shared set, so one extraction clears it), which suggests factoring
  the existing pair→group collapse rather than duplicating it.

## Verification

Per `scripts/type-overlap-check.README.md` §6.9, assert the failure mode as well
as the success one: a throwaway pair of types both spelling `A & B` must exit 1
and name both locators, and must go clean once the combination is named.

Sweep at the time of PR #11: `Titled & Described` in `components/Card.tsx` was
the repo's only repeated combination, so the gate would land green today.
