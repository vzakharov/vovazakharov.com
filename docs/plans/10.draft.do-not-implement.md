# Issue #10 — deliver the Playgram case study onto the website

Issue: https://github.com/vzakharov/vovazakharov.com/issues/10 · export at `docs/issue/10/issue.md`

## The question the issue actually asks

> The zero-approximation question we need to answer is: how do we deliver content at all?

The answer this plan commits to: **markdown is the source of truth, and it is compiled to HTML at build time, in Node, inside a server component.** The site is a static export, so "build time" is the only time there is — every page is already HTML on a CDN. That means the markdown toolchain (`unified`, `remark`, `rehype`, `shiki`) never reaches the browser: it runs once per deploy and leaves nothing behind but markup. **The baseline client cost of a content page is zero bytes of JavaScript beyond what the site already ships** (theme toggle), which is the property the issue's bundle-size worry is really asking for.

The two alternatives named in the issue are both rejected, for stated reasons:

- **Re-narrating the markdown as a React component** couples prose to JSX, guarantees drift between the in-repo document and the published one, and makes every future article a hand-build. It also throws away the thing the issue wants preserved — the original markdown as a downloadable artifact.
- **Parsing the markdown on the client** ships a parser (and a highlighter, and a diagram renderer) to every reader, renders nothing until JS executes, and gives crawlers an empty page. It is strictly worse than doing the same work once at build time.

Not split-worthy: this is one cohesive problem statement — a content pipeline and its first document — not an enumeration of independent deliverables. The CV addition the issue asks for as "riding along" is 3 files on its own, well under the bar for a PR of its own, and belongs in the same change as the case study it links to.

## Open questions

Each has a recommendation, and **the plan below is written with every recommendation already in force** — so silence is a valid answer and the plan is implementable as it stands. Answer tersely (e.g. "1a, 2b, 3-default").

**1 — Where do case studies live in the URL space?**

- **(a) `/case-studies/<slug>` — recommended.** Says what it is; leaves `/writing` to mean the Glitchporn essays the homepage already points at, and leaves room for a future `/notes` or `/articles` collection alongside.
- (b) `/writing/<slug>` — reuses the homepage's existing section vocabulary, but conflates technical case studies with the fiction/essay output.
- (c) `/work/<slug>` — shorter, but vaguer, and overlaps conceptually with the CV.

**2 — The screen recording (8.3 MB, `video/quicktime`) currently hotlinked from `github.com/user-attachments`.**

- **(a) Vendor it — recommended.** Download, transcode to MP4 (H.264/AAC, `+faststart`) with `ffmpeg`, commit under the collection's `assets/`, reference it relatively. Reason: the asset serves as `video/quicktime`, which **Firefox will not play** — so hotlinking ships a broken player to a slice of readers of the site's flagship piece. Vendoring also removes an external runtime dependency for first-party content. Cost: roughly 4–8 MB in git (the repo already carries 2.6 MB of case-study PNGs). The one remote `<img>` in the document (359 KB PNG) gets vendored in the same pass, for consistency.
- (b) Keep hotlinking, wrap in `<video>`, accept the Firefox gap and the external dependency. Zero repo weight.

**3 — The two Mermaid diagrams.**

- **(a) Pre-render to committed SVG, keyed by a hash of the fence — recommended.** An authoring script renders each `mermaid` fence to a light and a dark SVG; the build substitutes them and **fails loudly** if a fence has no matching render, so the diagrams cannot silently drift from their source. The markdown keeps its `mermaid` fence, so GitHub still renders it natively. Ships zero client JS. Verified working in this session: `pnpm dlx @mermaid-js/mermaid-cli` renders this document's import graph in ~30 KB against the preinstalled Chromium, so nothing is added to `package.json` and CI never touches puppeteer.
- (b) A client island that dynamically imports `mermaid`. No authoring step, but ~1 MB of JS on a page whose whole point is that it loads fast.

**4 — Where does content live on disk?**

- **(a) Move `content/` → `public/content/` — recommended.** The issue asks for the original markdown to be downloadable and wonders whether to "store in `public/`". Since the raw markdown _is_ a published artifact, `public/` is where it belongs by the meaning `public/` already has on this project. One copy of every file, served raw at `/content/…` for free, no build step to forget, no generated tree, no possible drift between the authored and the published document. Relative links inside the documents (`./assets/…`, `./…mini.md`) keep resolving in the served copy exactly as they do in the repo.
- (b) Keep authoring in `content/` and copy it into `public/content/` in a `prebuild`/`predev` step, gitignoring the copy. Keeps `public/` free of prose, at the cost of a build step, a generated directory, and staleness whenever the step is skipped.

## What gets built

### 1 — Content on disk

`git mv content public/content`. The tree becomes:

```
public/content/
  case-studies/
    playgram-bubble-to-nextjs-part-1.md            # full
    playgram-bubble-to-nextjs-part-1.mini.md
    playgram-bubble-to-nextjs-part-1.micro.md
    assets/                                        # authored: png, csv, svg, mp4
  generated/
    mermaid/<hash>.light.svg, <hash>.dark.svg      # committed, produced by the script in §4
```

Each document gains YAML frontmatter carrying **only what the markdown cannot already express** — no `title` field, because the title is the document's first `# ` heading and duplicating it invites drift:

```yaml
---
description: ... # meta description + index-card blurb
date: 2026-08-29 # published date, ISO
part: I of II # optional free-text series marker
ogImage: ... # optional, relative to the document
---
```

`title`, `wordCount`, reading time and the heading outline are all **derived** from the document at build time.

Content edits to the three documents, beyond frontmatter:

- The bare `github.com/user-attachments/…` video URL becomes a relative markdown link to the vendored MP4 on its own line, with the link text serving as the video's accessible label. GitHub renders it as a link; the site renders a player.
- The one raw `<img src="https://github.com/user-attachments/…">` becomes a relative markdown image.

### 2 — The pipeline (`lib/content/`)

Every module starts with `import 'server-only'` — this code must never be reachable from a client component.

| Module           | Responsibility                                                                                                                                                           |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `collections.ts` | The one registry of collections: `{ 'case-studies': { dir, routeBase, label } }`, with `CollectionId` derived from it. `VARIANTS = ['mini','micro'] as const`, likewise. |
| `frontmatter.ts` | Zod schema for the block above; the TS type is `z.infer` of it, never hand-written. Parsing (not casting) a loosely typed `gray-matter` result is the boundary check.    |
| `documents.ts`   | Enumerate a collection, parse `<slug>[.<variant>].md` filenames into `{ slug, variant }`, resolve sibling variants, expose `listDocuments()` / `loadDocument()`.         |
| `render.ts`      | The `unified` pipeline; returns `{ html, title, headings, wordCount }`. Module-level memo so the index page and the article pages parse each file once per build.        |

Pipeline: `remark-parse` → `remark-gfm` → (extract + strip the leading `h1` as the title; count words) → `remark-rehype` with `allowDangerousHtml` → `rehype-raw` → `rehype-slug` → `rehype-autolink-headings` → the local plugins below → `@shikijs/rehype` → `rehype-stringify`.

Raw HTML passes through unsanitized: the content is first-party, authored in this repo, and reviewed in the same PR as the code. There is no user-submitted content anywhere on this site, so a sanitizer would only strip the author's own `<br>` and iframes.

Local rehype plugins, one file each under `lib/content/plugins/`:

- **`rehypeContentLinks`** — rewrites relative `*.md` links to their site routes (`./x.mini.md` → `/case-studies/x/mini`), relative asset links to `/content/…`, and marks off-site links `target="_blank" rel="noopener noreferrer"`. This is what makes the documents' existing in-prose cross-links between full/mini/micro work on the site.
- **`rehypeMediaEmbeds`** — a paragraph whose only child is a link to a video file becomes `<video controls preload="metadata" playsinline>` with the link text as its label and a fallback download link inside.
- **`rehypeImageDimensions`** — reads intrinsic dimensions off the file (PNG `IHDR`; SVG `viewBox`) to set `width`/`height` so images reserve their space, plus `loading="lazy" decoding="async"`. No dependency; ~30 lines.
- **`rehypeMermaid`** — replaces a `language-mermaid` code block with the light and dark SVGs from `public/content/generated/mermaid/`, keyed by a hash of the fence text, as two `<img>` swapped by CSS on `.dark`. **Throws** when a hash has no render, naming the script to run.
- **`rehypeTableScroll`** — wraps every `<table>` in an `overflow-x-auto` container. The document has tables far too wide for a phone.

Shiki runs with `themes: { light: 'github-light', dark: 'github-dark' }`, `defaultColor: false` (CSS-variable output, swapped on `.dark`), `fallbackLanguage: 'text'` so an unknown fence language never fails a build, and `langs` limited to those the content actually uses.

### 3 — Routes, pages and components

| Path                                  | What                                                                                                                                                                                                                                           |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `app/case-studies/page.tsx`           | Index: one card per document (title, description, date, reading time, variant links).                                                                                                                                                          |
| `app/case-studies/[...slug]/page.tsx` | One catch-all covers the base document and its variants; `generateStaticParams` comes from the registry, so a new markdown file is a new page with no route work. `generateMetadata` builds `ogType: 'article'` metadata from the frontmatter. |
| `app/sitemap.ts`                      | Static routes plus every document, derived from the registry.                                                                                                                                                                                  |

Unlocalized, alongside `/` rather than under `[locale]`: the content is English-only markdown, and inventing a `ru` route for a document that does not exist in Russian would only produce a duplicate. The seam for later is a `<slug>.<locale>.md` filename convention, noted in the docs, not built.

Components under `components/content/`:

- `ArticleHeader` — title, description, date, reading time, the full/mini/micro switcher, and a **"Markdown" link to the raw document** at `/content/case-studies/<file>.md` (the issue's downloadable-original ask).
- `TableOfContents` — the derived `h1`/`h2` outline, sticky on wide viewports, plain anchors and no JavaScript. `h1` is a part divider in this document, so the outline nests `h2` under it.
- `ArticleBody` — the rendered HTML, `prose` classes, `dangerouslySetInnerHTML`.

Styling: install `@tailwindcss/typography` and set the `--tw-prose-*` variables from the site's existing `--foreground`/`--background` tokens in a new `app/prose.css`, so both themes work without a single `dark:` utility — matching how the rest of the site themes itself. Also there: the Shiki and Mermaid light/dark swaps and the table-scroll container.

One cleanup this forces: `app/HomePage.tsx` carries `prose prose-invert` classes that do nothing today (the plugin was never installed). Installing it would suddenly restyle those blocks, so the vestigial classes come off in the same commit.

### 4 — `scripts/render-mermaid.mjs`

Walks every markdown document, hashes each `mermaid` fence, and for any hash without a cached render invokes `pnpm dlx @mermaid-js/mermaid-cli` twice (`-t default`, `-t dark`, transparent background, `--svgId` per render) into `public/content/generated/mermaid/`. Prunes renders no fence refers to any more. Discovers Chromium from `PUPPETEER_EXECUTABLE_PATH`, then `/opt/pw-browsers/chromium-*/chrome-linux/chrome`, then the system binary; errors with the fix if it finds none. Exposed as `pnpm content:mermaid`.

Invoked by hand when a diagram changes — never by `next build`, so CI stays free of puppeteer and the deploy stays fast. The build's hard failure on a missing render is what keeps that honest.

### 5 — Reaching the content

- **Homepage**: a "Case studies" block in `/dev`, above Featured Projects, with a card for the piece. Without this the article is unreachable from the site.
- **CV** (the issue's "riding along"): a Playgram entry as the most recent experience, plus a short "Case studies" section linking to the write-up, in `en.json` and `ru.json` both.
- `cv.experience`'s five hardcoded `<Card>` blocks in `CVPage.tsx` collapse into one `ExperienceCard` driven by an ordered key list, because adding a sixth by copy-paste is how a 373-line file becomes a 450-line one. Message keys move from positional (`project1`, `project2`) to slugs (`englishForKids`, `orcool`, …); order lives in code, where it is a presentation decision, so `en` and `ru` cannot drift on it. The two item shapes already in the catalogs (`string[]` and `{label,text}[]`) are both handled rather than migrated.

### 6 — Docs

`CLAUDE.md` gains a **Content** section: the `public/content/` layout row, the build-time-only rule and why, how to add a document, the Mermaid cache contract, and the locale seam. `docs/plans/10.*.md` and `docs/issue/10/` ride the branch and are swept by `/finalize`.

## DRY notes

- **Genuinely shared, extracted once:** the markdown→HTML pipeline (`lib/content/render.ts`) — the index page, the article pages and the sitemap all consume the same registry and the same renderer; the collection/variant registry, which is the single place a URL shape is decided; `lib/metadata.ts`, extended rather than duplicated, so article metadata goes through the same `constructMetadata` as the CV.
- **Reused as-is:** `constructMetadata` (`ogType: 'article'` is already in its union), `ThemeToggle`, `Card`, `SITE_CONFIG`, `getAbsoluteUrl`.
- **Deliberately not extracted — a page shell for `/`, `/cv` and the article.** All three open with `min-h-screen p-8 pb-20 sm:p-20` and a `max-w-4xl` centre column, so a `PageFrame` looks tempting. It would be a false abstraction: the CV's wrapper carries print variants nothing else wants, the article needs a wider grid with a TOC rail and no `max-w-4xl`, and the homepage needs neither. The shared part is four utility classes; the differences are the whole layout. Wrapping them would mean a component with three mutually exclusive modes, which is worse than four repeated classes.
- **Deliberately not extracted — the rehype plugins into one module.** Five small plugins in five files, not one `plugins.ts`, because each is independently testable and only the pipeline knows they compose.
- **Duplication removed on the way through:** the five near-identical CV experience cards (§5). Not a new abstraction invented for its own sake — it is the copy-paste this change would otherwise extend to six.
- **Not duplicated:** document titles, word counts and heading outlines are derived from the markdown, never restated in frontmatter or in a registry file; the Mermaid renders are keyed by a hash of their own source, so a stale render fails the build instead of shipping.

## Known limitations, stated rather than discovered later

- `public/content/case-studies/assets/playgram-commit-cumsum.svg` themes itself with `@media (prefers-color-scheme: dark)`. Referenced as an `<img>`, that follows the **system** preference, not the site's theme class, so a reader whose system is light but who has toggled the site to dark gets a light chart. Fixing it properly means teaching that asset to take its colours from inherited CSS custom properties and inlining it. Out of scope; worth its own issue.
- No Open Graph image of its own — the metadata falls back to the avatar. `ogImage` is in the frontmatter schema for whenever a card gets drawn.
- The raw `.md` files are crawlable alongside the rendered pages, and GitHub Pages cannot set `X-Robots-Tag`. Cosmetic SEO duplication; the alternative is not publishing the originals, which the issue explicitly asks for.
