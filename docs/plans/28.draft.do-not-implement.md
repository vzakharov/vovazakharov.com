# #28 — Re-window the before/after rates on the commit-cumsum chart

Issue export: `docs/issue/28/issue.md`. Closes #28.

The chart reports the switch into the cloud as **6.2 → 8.2 units of work per day**. Both windows are drawn wrong: the "before" window starts inside a docs-only phase, and the "after" window runs four months past the point where the job changed, over calendar days that include every weekend and a week off. This plan picks four defensible dates, recomputes both rates over working days, draws the windows on the chart, and brings the prose and alt text into line.

## Where the numbers come from

**The Playgram repository, not the picture.** `Playgramai/playgramapp` was cloned to `tmp/playgramapp` (`gh repo clone … -- --filter=blob:none --no-checkout --single-branch --branch main`) and every date below is read off its commit history. The committed dataset — `public/case-studies/assets/playgram-commit-cumsum.csv` — cannot answer the questions the issue asks, because documentation-only commits are already filtered out of it: a docs-only *phase* looks identical to a holiday there.

Classifying a commit as documentation-only when every path it touches is `*.md`, `docs/`, `.claude/` or `bubble/` (the Bubble export dump) reproduces the chart's headline exactly — **1,287 code commits, 6 Mar – 21 Aug 2026**.

### The docs-only phase ends on 11 March

Code commits against documentation commits, per day, from the repository:

| Date | Day | Code | Docs |
| --- | --- | --- | --- |
| Fri 6 Mar | 0 | 3 | 13 |
| Sat 7 Mar | 1 | 0 | 1 |
| Sun 8 Mar | 2 | 0 | 0 |
| Mon 9 Mar | 3 | 0 | 12 |
| Tue 10 Mar | 4 | 1 | 22 |
| **Wed 11 Mar** | **5** | **16** | **9** |

Documentation is the work through 10 March and stops being the work on 11 March. The article's own timeline table already says as much — "6 Mar · First commit. Not code — a splitting script and a pile of research" — so the date is consistent with the prose, not invented for the chart.

### The break is 7–10 May, and the weekends are everywhere

The switch into the cloud falls on **Saturday 25 April** (4 commits that day, none on the Sunday); the first full working day in the cloud is **Monday 27 April**. Work then runs hard — including the weekend of 2–3 May — before stopping:

| Date | Code commits |
| --- | --- |
| Tue 5 May | 16 |
| Wed 6 May | 3 |
| Thu 7 May – Sun 10 May | 0, 1, 0, 0 |
| Mon 11 May | 10 |

That is the "days off" gap in the annotation. It is not the only idle time: of the 118 calendar days in the currently-published "after" window, only 89 were worked. Measuring over working days removes the break and every weekend at once, which is why the issue asks for it rather than for a hand-cut window around the break.

### `4.1.0` is 24 June

Confirmed against the repository's tags (`4.1.0 → 2026-06-24`). Before it the job was shipping the Bubble-parity app; after it, bug fixes and new features. The chart already plots the `4.1.0` dot at that date, so the window's right edge lands exactly on an existing mark.

## The four dates and the two rates

| | Window | Commits | Working days | Rate |
| --- | --- | --- | --- | --- |
| **Before** | 11 Mar – 24 Apr | 307 | 34 | **9.0 / working day** |
| **After** | 27 Apr – 24 Jun | 611 | 44 | **13.9 / working day** |

A working day is a day with at least one code commit — the same rule for both windows, no threshold and no hand-picking.

The switch weekend (25–26 April) belongs to neither window: 25 April is the switch itself, and a Saturday.

**The effect is larger than the published figure says.** 6.2 → 8.2 is a factor of 1.32; 9.0 → 13.9 is **1.54** — half again as much work per working day, not a third more. The weekly panel agrees independently: the median week goes from 44 units before the switch to 74 after, a factor of 1.68.

### Which dataset the rates are computed from

**The committed CSV, not the fresh clone** — deliberately, and this is the one place the repository is not the source.

The chart's curve is drawn from the CSV. A rate label printed beside a curve has to be the slope of *that* curve, or the picture and the number disagree — which is the exact defect the issue is filed about. Recomputing the rates from today's clone while leaving the curve alone would print 13.0 next to a line that rises at 13.9.

So: the repository supplies the four **dates** (which only it can), and the CSV supplies the **counts** behind them.

**Finding worth recording:** the committed CSV no longer reproduces exactly from the repository as it stands today. The totals agree (1,287 either way) and the daily counts track closely (mean absolute difference 0.95 commits/day), but they are not identical — 23 March is the largest divergence, 10 code commits in the clone against 0 in the CSV, which is the signature of history rewritten after the CSV was generated. Over the proposed "after" window the two datasets differ by about 6% (611 against 573), i.e. 13.9 against 13.0 per working day. Regenerating the dataset and redrawing the curve from it is a real option — see question 3 — but it is a larger change than this issue asks for, and it moves the picture rather than the annotation.

## Open questions

Each carries a recommendation, and the plan above is written with the recommendation already in force. Answer tersely (e.g. "1a, 2b") or say nothing and the recommendations stand.

**1. Where does the "after" window start?**

- **(a) 27 April — the first full working day in the cloud (recommended).** The break's idle days fall out of the denominator on their own, so the 27 Apr – 6 May stretch stays in the measurement instead of being discarded. It also keeps the window's left edge at the thing being measured — the switch.
- (b) 11 May — the day work resumes after the break, which is the issue's literal wording ("the stretch that begins once work resumes after the break"). Gives 14.9 per working day, a factor of 1.65. It throws away eight working days of cloud-era work to avoid days the working-day denominator already excludes.

**2. Where does the "before" window start?**

- **(a) 11 March — the first day code outweighs documentation (recommended).** Falls straight out of the repository's per-day split, no judgement needed.
- (b) 12 March — "first feature code" per the article's own timeline table, which would tie chart and table to one date. Costs one working day and reads as tuning.

**3. Regenerate the dataset from the repository?**

- **(a) No — keep the committed CSV and change only the annotation (recommended).** The issue is about the windows, not the curve. Keeps the change reviewable and the picture stable.
- (b) Yes — regenerate `playgram-commit-cumsum.csv` from the clone with the documented rule, redraw the curve, bars and dots from it, and commit a script that does it. Makes the whole artifact reproducible and closes the ~6% divergence, but it needs a chart generator this repo does not have, and it redraws a picture nobody has complained about. Worth its own issue if wanted.

## DRY notes

- **The alt text stays triplicated across the three cuts.** It is identical in `playgram.md`, `playgram.mini.md` and `playgram.nano.md`, and it is tempting to extract. Don't: the content pipeline reads each markdown file as an independent published artifact served raw at its own URL (`.claude/rules/content.md`), so a shared fragment would need an include mechanism the pipeline does not have and would break the property that the `.md` in the repo, on GitHub and on the site are the same bytes. Three coordinated edits is the correct cost.
- **The four dates are stated once per surface, and the surfaces are genuinely different audiences** — the SVG's visible labels, the SVG's `<desc>`, and the prose in two cuts. There is no shared runtime between an SVG served as an image and markdown compiled at build time, so a single source of truth for them would mean generating the SVG, which is question 3(b), not a refactor.
- **No new helper, module or type is added.** The change is text and geometry inside one committed SVG plus prose in three markdown files. The x-scale arithmetic (`66 + day × 4.25`) is applied once, by hand, to six marks — extracting a function for six literals in a static asset would be worse than the literals.
- **The analysis scripts stay in `tmp/`.** The per-day classification used to pick the dates is throwaway: it reads a clone that is not part of this repository and cannot run in CI. Under question 3(a) nothing about it belongs in `scripts/`; under 3(b) it becomes the generator and is written properly then.
